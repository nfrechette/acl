    Creating a raw track list¶

    Once you have an allocator instance, the next step is to create a raw track list and populate it with the data we will want to compress. Doing so is fairly straight forward and you will only need a few things:

    • An allocator instance
    • The number of tracks (a track array cannot be resized)
    • The number of samples per track (each track has the same number of samples)
    • The rate at which samples are recorded (e.g. 30 == 30 FPS)
    • Access to the Realtime Math headers since its types are used by the API
    #include <acl/compression/track_array.h>

using namespace acl;

uint32_t num_tracks = 4;
uint32_t num_samples_per_track = 20;
float sample_rate = 30.0f;
track_array_float3f raw_track_list(allocator, num_tracks);

    Once you have created an instance, simply populate the track data. Note that at the moment, tracks contained in the array are untyped but they must all have the same track type (e.g. float2f), the same number of samples per track, and the same sample rate.

    Each track requires a track description. It contains a number of important properties:

    • output_index: after compression, this is the index of the track. This allows re-ordering for LOD processing and other similar use cases.
    • parent_index: for transform tracks, indicates the parent transform index it is relative to (in local space of).
    • precision: the precision we aim to attain when optimizing the bit rate. The resulting compression error is nearly guaranteed to be below this threshold.
    • shell_distance: for transform tracks, indicates the distance at which we measure the error, see error metric function.
    track_desc_scalarf desc0;
desc0.output_index = 0;
desc0.precision = 0.001F;

track_desc_transformf desc1;
desc1.output_index = 0;
desc1.parent_index = 0;
desc1.precision = 0.01F;
desc1.shell_distance = 3.0F;

    Tracks can be created in one of four ways:

    • make_copy(..): creates a new track and copies the data internally. The new instance owns the memory and the original data is no longer required.
    • make_reserve(..): creates a new track and allocates the required memory without initializing it. It owns the new allocated memory.
    • make_owner(..): creates a new track and takes ownership of the provided source pointer. No copy takes place.
    • make_ref(..): creates a new track and references the provided source data. No copy takes place and the new instance does not own the referenced memory.

    make_owner(..) and make_ref(..) are handy when the track data is already allocated somewhere and doesn't need to be copied explicitly. Functions that take source data as input also support a custom stride and make no assumption about the data layout for utmost flexibility.

    track_float3f raw_track0 = track_float3f::make_reserve(desc0, allocator, num_samples, sample_rate);
raw_track0[0] = rtm::float3f{ 1.0F, 3123.0F, 315.13F };
raw_track0[1] = rtm::float3f{ 2.333F, 321.13F, 31.66F };
raw_track0[2] = rtm::float3f{ 3.123F, 81.0F, 913.13F };
raw_track0[3] = rtm::float3f{ 4.5F, 91.13F, 41.135F };
// ...
raw_track_list[0] = std::move(raw_track0);

    Once your raw track list has been populated with data, it is ready for compression. The data contained within the track_array will be read-only.

    Each sample of a scalar track can also select how it interpolates to the next sample, for example to make a step. See extended samples for details.

    You can override the looping policy by calling raw_track_list.set_looping_policy(policy);. This is only necessary if you perform your own loop optimization before compressing with ACL. See how to handle looping playback for details.

    Transform tracks¶

    ACL supports three transform track types:

    • vqvf (track_vqvf, track_array_vqvf): each sample is a rtm::vqvf with a rotation, a translation, and a 3D scale.
    • vqsf (track_vqsf, track_array_vqsf): each sample is a rtm::vqsf with a rotation, a translation, and a uniform scale. The scale is in the W component of translation_scale.
    • vqf (track_vqf, track_array_vqf): each sample is a rtm::vqf with a rotation and a translation. A VQ track has no scale.

    The three types use track_desc_transformf as their description. With vqf, ACL ignores the scale of default_value. With vqsf, ACL uses the X component of the scale of default_value.

    The compressed tracks keep the type of the raw tracks. Thus a VQV clip without scale gives a compressed VQV clip. To convert the raw tracks from one type to another, use the convert_transform_type pre-process action.

    When you decompress a VQ clip, ACL does not write the scale: it does not call write_scale on your track writer. If you use your own decompression settings, is_track_type_supported must return true for track_type8::vqf to decompress a VQ clip.

    A compressed VQS clip stores one value for each scale sample, thus an animated uniform scale uses a third of the memory of a VQV scale. When you decompress a VQS clip, ACL writes the scale with this overload of your track writer:

    void RTM_SIMD_CALL write_scale(uint32_t track_index, rtm::scalarf_arg0 scale);

    When your track writer does not have this overload, ACL calls write_scale(uint32_t, rtm::vector4f_arg0) with the uniform scale in [xyzw]. If you use your own decompression settings, is_track_type_supported must return true for track_type8::vqsf to decompress a VQS clip. The default decompression settings for transform tracks accept the three types.

    track_desc_transformf desc;
desc.output_index = 0;
desc.precision = 0.01F;
desc.shell_distance = 3.0F;

track_array_vqf raw_transform_tracks(allocator, num_tracks);

track_vqf raw_track = track_vqf::make_reserve(desc, allocator, num_samples, sample_rate);
raw_track[0] = rtm::vq_set(rtm::quat_identity(), rtm::vector_set(0.0F, 1.0F, 0.0F));
// ...
raw_transform_tracks[0] = std::move(raw_track);

    Playback scale¶

    The runtime can play a clip at another scale than the scale of its authoring. For example, a designer scales a boss character, or the game spawns a character with a random scale. Then the error that you see is the object space error multiplied by that scale. Set the uniform scale of the clip at playback with set_playback_scale(..) on the track array:

    track_array_vqvf raw_transform_tracks(allocator, num_tracks);
// ...
raw_transform_tracks.set_playback_scale(4.0F);
    • The precision of each track, the keyframe stripping threshold, and the error that calculate_compression_error returns are in playback units. Thus a precision of 0.01 keeps the error at playback below 0.01.
    • The shell distance stays in the units of the clip.
    • Compression divides the precision by the playback scale: with a scale of 4.0 and a precision of 0.01, it compresses the clip as with a precision of 0.0025 and a scale of 1.0.
    • The compressed data does not store the playback scale: decompression does not use it. The track descriptions in the compressed data keep the precision that you set.
    • The playback scale must be positive and finite. It defaults to 1.0. Scalar tracks do not use it.
    • To compare two raw track arrays with calculate_compression_error, both must have the same playback scale.

    When the clip plays at different scales, use the largest scale.

    Additive animation clips¶

    If the clip you are compressing is an additive clip, you will also need to create an instance for the base clip. Put the base clip and the format of the additive clip in a transform_base_desc_t, and give it to compress_track_list(..). See the transform space for an example.

    When the transforms of the clip are not in local space, set the transform space of the track array with set_transform_space(..). See the transform space.

    The library assumes that the raw clip data has already been transformed to be in additive or relative space.

    The additive clip and its base clip can have different transform types (vqvf, vqsf, or vqf). A VQ track has no scale: in an additive clip, ACL uses the identity scale of the additive format (0.0 with additive1, 1.0 otherwise). In the base clip, ACL uses a scale of 1.0.

    Note that if your additive format does not use a scale of 1.0 as its default value, you will need to provide the desired value to ACL. See default sub-track handling for details.

    Re-ordering or stripping bones¶

    Sometimes it is desirable to re-order the bones being outputted or strip them altogether. This could be to facilitate LOD support or various forms of skeleton changes without needing to re-import the clips. This is easily achieved by setting the desired output_index on each track_desc_transformf contained in a track_vqvf, a track_vqsf, or a track_vqf. The default value is the track index. You can use k_invalid_track_index to strip the track from the final compressed output.

    Note that each output_index needs to be unique and there can be no gaps. If 20 bones are outputted, the indices must run from [0 .. 20).

    Compressing morph target blend weights¶

    Curves that drive a morph target (aka blend shape) are not ordinary and require special consideration. They ultimately drive an object space mesh deformation and as such we can leverage that information to reduce the memory footprint and simplify the task of choosing a suitable precision value.

    If you have access to the morph target deformation information, you can calculate the largest vertex displacement for a given curve. Once you have that value, use a morph target deformation precision value such as 0.1 mm and use the maximum vertex displacement to calculate the desired blend weight precision value like this:

    blend weight precision = vertex precision / vertex displacement delta

    See here for more details.

    Using custom default sub-track values¶

    By default, ACL assumes that sub-tracks have the identity as their default value. This is nice and simple but it is not always optimal. If a character has many animation compressed, it might be better to use its bind pose as the default value instead. See default sub-track handling for details.
